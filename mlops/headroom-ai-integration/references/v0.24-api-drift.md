# headroom-ai v0.24 — API drift from older plans and docs

Quick lookup for the differences between headroom-ai ≤ 0.5 (what most online
docs and the original `~/llm-server/context-compression-plan.md` were written
against) and v0.24+ (what's actually in production).

If you're reading the plan in `~/llm-server/context-compression-plan.md`, the
plan was patched 2026-06-13 to match v0.24 — but other docs and StackOverflow
answers may not be. When in doubt, introspect the live library:

```python
import inspect
from headroom import CompressConfig, compress
print(inspect.signature(CompressConfig.__init__))
print(inspect.signature(compress))
cfg = CompressConfig()
import dataclasses
print([f.name for f in dataclasses.fields(cfg)])
```

## Field renames

| Old (≤ 0.5) | v0.24 | Notes |
|---|---|---|
| `strategies=["code", "json"]` | **(removed)** | Content router auto-picks |
| `min_chars=4000` (custom gate) | `min_tokens_to_compress` (in `CompressConfig`) | Now library-internal |
| `protect_recent=2` | `protect_recent=4` | Default raised |
| `target_ratio=0.5` | `target_ratio=0.5` | Same |
| — | `compress_user_messages=False` | New v0.24 default; user turns preserved |
| — | `protect_analysis_context=True` | New v0.24 default; CoT/reasoning blocks protected |
| — | `kompress_model=None` | New v0.24; optional HF model for prose |

## Result field renames

```python
# v0.5 era
result.original_tokens
result.compressed_tokens
result.messages

# v0.24
result.tokens_before         # was original_tokens
result.tokens_after          # was compressed_tokens
result.tokens_saved          # new: tokens_before - tokens_after
result.compression_ratio     # NEW — float (after/before); 0.36 = 64% saved
result.transforms_applied    # was transforms; values changed semantics too
result.messages              # same
```

## `transforms_applied` semantics

In v0.24 the values are router-internal tags, not user-friendly strategy names:

```
'router:protected:user_message'           # user turn, not touched
'router:protected:recent_code'            # in protect_recent window
'router:protected:analysis_context'       # CoT/reasoning block protected
'router:text:0.42'                        # text compressor, ratio 0.42
'router:code:0.31'                        # code compressor (AST-aware)
'router:smart_crusher:0.28'               # JSON/structured
'router:mixed:0.26'                       # low-confidence classification
```

Don't pattern-match these as strategy names — they encode both the strategy
and the achieved ratio.

## What the content router actually picks

Auto-detected per message based on confidence scoring:

| Detected content | Strategy |
|---|---|
| Prose, docs | `text` |
| Source code, code blocks (AST-aware, 6 langs) | `code` |
| JSON, tool outputs, API responses | `smart_crusher` |
| Mixed / low confidence | `mixed` |

Confidence threshold is headroom-internal — not exposed in the public API.

## Common gotcha: `model` arg is required-ish

`compress(messages, model="...")` — v0.24 takes a `model=` kwarg. The default
is `'claude-sonnet-4-5-20250929'`, but for accurate content routing you should
pass the actual model name (e.g. `'qwen36-35b'`). Without it, the router picks
strategies calibrated for Claude which may not match your model's content
distribution.

## Install on Python 3.14

Rust extension build fails on PyO3 ≥ 0.22.6 because Python 3.14 is newer than
the supported version. Workaround:

```bash
PYO3_USE_ABI3_FORWARD_COMPATIBILITY=1 pip install "headroom-ai[proxy]"
```

Works against the existing `~/llm-server/venv` (Python 3.14).

## Failure mode: silent no-op

If `headroom` isn't installed, the proxy logs once at import time:
```
headroom-ai not installed — context compression disabled
```

`_compress_messages()` short-circuits on the first guard, so there's zero
runtime overhead. But the `◈` log line never fires and operators may think
compression is broken — they need to know to check the import-time log
specifically, not the per-request log.

## Performance baseline (Strix Halo, qwen36-35b, 131k ctx)

- 8-message chat with large tool output: ~5% net savings (most content is recent/protected)
- 26-message agentic loop: 96,190 → 34,394 tokens (64% reduction, 36% net after overhead)
- 30+ message long session: 219,596 → 54,956 tokens (75% reduction)
- First call: ~14s (HuggingFace tokenizer downloads)
- Warm calls: ~100ms (in-process cache)
- HuggingFace downloads land in `~/.cache/huggingface/` — pre-warm if you need first-call latency to be sane
